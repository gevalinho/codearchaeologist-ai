# Architecture

## Repository Intelligence and the Legacy Pricing example

The primary workspace at `/` provides local repository scanning, graph import, module and feature exploration, and evidence inspection. `/architecture` redirects to `/`. The Legacy Pricing example at `/examples/legacy-pricing` shows the trusted `legacy-pricing` source with line numbers, evidence-backed findings, verification status, cases, provider metadata, and limitations. `POST /api/investigate` accepts only `{ "fixtureId": "legacy-pricing" }`, requires explicit live provider configuration and a local opt-in flag, and runs the bounded Phase 2 orchestrator. It never imports or invokes Docker. `GET /api/demo-report` reads only `.local-demo/verification-report.json`, validates its source hash, evidence, reviewed cases, status consistency, and provenance, then displays it. This route never executes code.

The operator-only `npm run demo:report` command runs the same trusted fixture with the explicitly selected live provider, invokes the Phase 3 verifier, validates and sanitizes the report, and writes the ignored local artifact. A report says `ISOLATED_DOCKER` only when actual cases were executed; otherwise it says `NOT_EXECUTED` and retains `NOT_TESTED` or `BLOCKED` statuses. Mock providers are rejected by artifact validation.

CodeArchaeologist AI reconstructs business behavior from source and checks selected hypotheses against execution of the included pricing fixture. Phase 2.1 provides a bounded investigation workflow with separate server-only Meta Model API and Baseten adapters. Phase 3 adds opt-in, container-isolated verification.

## Data flow

1. A trusted server configuration selects an included fixture. The browser will never supply a filesystem path.
2. The repository inventory reads supported JavaScript and TypeScript files under that fixture, applies limits and exclusions, and records exact paths, content, byte counts, and line counts.
3. Evidence extraction resolves a file and inclusive line range against the inventory. Rule validation rejects unknown files, invalid ranges, and excerpts that differ from source.
4. For a single eligible source file, the bounded orchestrator selects it deterministically and records that decision. For multiple files, it sends metadata to the provider, constrains the response schema to inventoried path values, and validates the selection locally. It supplies only selected source (at most three files and 8,000 characters), then validates every cited line against the inspected inventory. A separate model review assesses whether each candidate follows from its evidence; rejected claims are retained with reasons. The original pricing fixture contains only `pricing.js`, so it uses two model calls rather than three. Accepted rules remain source-supported candidates, never `VERIFIED`.
5. The Meta and Baseten adapters implement the same `ModelProvider` interface. A server-only factory requires explicit live provider selection. Each adapter uses its own documented Chat Completions fields and JSON Schema format. The orchestrator budgets 3,000 output tokens for `candidate_rules` and 1,500 each for `review_rules` and multi-file `select_files`, while retaining three calls and a 30-second overall deadline. Requests have timeouts, up to two transient retries, sanitized errors, and bounded usage and latency accounting. `MockModelProvider` is injected only by tests; there is no mock fallback from live mode. The ordinary Vitest configuration excludes the paid smoke test, which has a separate explicit configuration.
6. `investigateAndVerify` runs the Phase 2 workflow, then matches supported candidates to reviewed pricing templates. Matching requires the exact normalized claim, precondition, outcome, and source lines in the pinned fixture. Unmatched or rejected claims remain `NOT_TESTED`. Only the trusted templates supply executable inputs and expected observations; model-supplied tests and paths are ignored.
7. The server-only verifier checks the fixture hash, Docker daemon seccomp, and the local Node image, then launches that image by ID. Docker runs the pinned fixture and a fixed runner with no network, read-only mounts and root filesystem, an unprivileged user, dropped capabilities, process, CPU, and memory limits, and a five-second deadline. The runner returns observations as JSON. Local code validates their shape and compares each observation with its reviewed expectation. A rule is `VERIFIED` only when all assigned cases pass. Failed comparisons, malformed output, and timeouts are `FAILED`; missing isolation is `BLOCKED`.

The current fixture, `tests/fixtures/legacy-pricing/pricing.js`, includes loyalty and promotion precedence, rounding, and a shipping threshold. The inventory does not parse syntax yet; selection relies on file metadata and bounded source review.

## Domain contracts

`src/types/investigation.ts` defines investigation lifecycle, inventory, evidence, actions, rules, declarative verification cases, observations, results, and reports. `src/lib/schemas/investigation.ts` validates evidence and the minimal candidate rule shape at runtime. The orchestrator forces `NOT_TESTED` irrespective of model output. The Phase 3 verifier alone computes final verification statuses and records inputs, expected and observed outputs, source evidence, and investigation actions.

Meta contract checked against [Meta Chat Completions](https://dev.meta.ai/docs/protocols/chat-completions) and [structured output](https://dev.meta.ai/docs/structured-output): `POST https://api.meta.ai/v1/chat/completions`, bearer key, `model`, `messages`, `response_format.json_schema`, `max_completion_tokens`, and `choices[0].message.content`. The default documented model is `muse-spark-1.3`; set `MODEL_API_KEY`, and optionally `META_MODEL_ID` or `META_MODEL_ENDPOINT`, on the server. No live call was made without credentials.

Baseten contract checked against its [official OpenAPI specification](https://docs.baseten.co/reference/inference-api/llm-openapi-spec.json): `POST https://inference.baseten.co/v1/chat/completions`, bearer key, `model`, `messages` with `system` and `user` roles, `response_format.json_schema`, `max_tokens`, and `choices[0].message.content`. The published Muse Spark Open slug is `meta-models/muse-spark-open`; the user confirmed the hackathon-specific `meta-models/muse-spark-open-1026` from onboarding, so it is the adapter default. See [provider configuration](environment.md).
