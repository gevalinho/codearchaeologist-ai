# B5.3 executable scanner worker

`scripts/scanner-worker.ts` is a single-job Node 24 entry point. It accepts exactly two generated UUID arguments: job ID and dispatch generation. It uses fixed spool subdirectories under `CODEARCH_SPOOL_ROOT` and a private worker-owned `CODEARCH_WORKER_SCAN_ROOT`. The worker validates both IDs and the spool ownership/modes, atomically claims the dispatch, publishes a receipt, waits for the matching web acknowledgement, then copies only manifest-listed files into a fresh worker-owned scan directory. It reopens each source with `O_NOFOLLOW`, verifies owner, group, mode, link count, size, and SHA-256, and checks the aggregate byte budget. The entry point sets umask 0022 so the fixed non-root container can read its copied source through a read-only bind mount. It invokes `scannerAvailable` and `runIsolatedScanner` with the existing fixed image and sandbox options. Dispatch metadata cannot choose Docker arguments, image, command, or mount path.

The worker polls cancellation and the dispatch deadline. A one-second worker-owned heartbeat file can be validated by the web side and used to renew its SQLite dispatch heartbeat. A cancellation or deadline aborts the active scanner signal. The worker publishes only a bounded, hash-checked result envelope and removes its temporary scan copy. It **retains the claim and receipt** after errors or crashes; no job is automatically retried. The web must reconcile ambiguous jobs as failed.

The worker entry point rejects inherited GitHub App, session database/encryption, and AI-provider credentials. It does not import `dispatch-store.ts`, open SQLite, or make GitHub or AI requests. Start it only with a minimal worker-specific environment. The `scanner:worker` package script does not read `.env.local`.

Production Docker calls additionally require the actual process UID to match a **root-owned**, non-group-writable, non-world-writable regular file at `/etc/codearchaeologist/scanner-worker-identity.json` containing exactly `{"webUid":<number>,"workerUid":<number>}` with distinct positive UIDs. The web identity must not be the worker UID. This code check is defense in depth; the real boundary is Unix ownership and a Docker daemon/socket available only to the worker identity. No identity file or OS accounts are created by this phase.

## Still required before production scanning

- The web job manager still performs acquisition and Docker scanning in one process in development. Production job creation remains HTTP 503. A later phase must split acquisition into the spool and wire web-side receipt acknowledgement, heartbeat observation, validated result reconciliation, authorization recheck, and private artifact publication through the existing job store.
- The web must atomically connect each receipt, acknowledgement, heartbeat, and result to the same current SQLite job lease/generation. Spool heartbeats alone do not renew SQLite leases. A lost web process, expired deadline, or ambiguous worker state must fail rather than retry.
- On the target host, verify separate web/worker UIDs, dedicated narrow spool groups, no worker access to the web SQLite database or credential files, no web access to Docker or Docker-capable sudo, and worker-only Docker access. A rootful Docker socket is host-equivalent privilege; evaluate a worker-only rootless daemon and verify seccomp probes, mounts, and cleanup under the real service accounts.
- Provide private persistent spool and worker scan roots with the modes documented in `scanner-spool-foundation.md`. The worker scan root must be worker-owned, canonical, and mode 0700. Configure the worker with only the spool paths and numeric ownership variables; do not inherit the web environment file. Deploying and activating the worker remain separate tasks.
