# Repository intelligence engine

Run locally with `npm run archaeology -- --repo /absolute/path/to/repository`. `ARCHAEOLOGY_REPO_ROOT=/absolute/path/to/repository npm run archaeology:scan` remains supported. Use `--out /absolute/local/output-directory` to select an output folder; the default is `.local-archaeology` under the current directory. The command reads only application PHP and JavaScript plus named application scripts in `assets/js`. It writes `graph.json` and `manifest.json` to the output directory. The default directory is gitignored. Do not commit artifacts from private repositories when using a custom output directory. Import `graph.json` directly into `/` with **Import graph JSON**.

The manifest records the graph schema and snapshot ID, UTC scan time, repository display name, source-derived scan and extraction counts, PHP and JavaScript file detections, warnings, coverage limitations, and artifact filenames. Counts describe scanned files and extracted records, not repository-wide coverage estimates. Neither artifact includes absolute repository paths or source snippets. Scanning runs locally, never executes repository code, and does not call the model provider or expose a server route. A future integration should use a separately installed, user-authorized local companion scanner that returns only validated artifacts to the browser; browser directory selection alone cannot provide reliable unrestricted repository scanning or the same filesystem protections.

The version 1.0.0 graph has a content-derived snapshot ID, typed nodes and edges, relative source references, observed or inferred certainty, extraction method, deterministic order, warnings, and limits. Contents and absolute paths are omitted. JavaScript and TypeScript use Babel syntax analysis; PHP uses pinned `php-parser@3.7.0` without executing source. The PHP facade indexes namespaces, imports, classes, interfaces, traits, enums, functions, and methods with source positions. It accepts PHP 5.0–5.6, 7.0–7.4, and 8.0–8.4 syntax modes, limits each source to 2 MiB, and bounds AST indexing to 100,000 nodes per file, 250,000 nodes per scan, and depth 256. Syntax and resource problems are reported generically without including source text. AngularJS UI-Router state declarations receive a separate route-focused AST walk capped at 10,000 nodes and depth 512; hitting that cap retains recovered states while warning that routing coverage is partial. State metadata preserves static state names, URL patterns, template URLs, explicit controllers, and source references. The additional walk does not raise general parser or AST limits.

Route extraction supports static CodeIgniter 3 `$route` entries, CodeIgniter 4 route collection verbs/groups, and Laravel route helpers/groups plus a small tested set of resource mappings. Framework detection is separately labeled confirmed, probable, or unknown; missing or ambiguous controller methods and dynamic declarations are not connected to invented graph nodes. Unsupported and dynamic forms mark coverage partial. PHP source selection still admits only established application roots and four exact route-manifest paths; it does not broaden access to other configuration files, dependencies, environment files, credentials, or secrets. The sole named bundle exclusion is the exact relative path `assets/js/echarts.js`; it is excluded before file reading in browser and local scans, with a warning and skipped-file coverage count. No general first-party size limit is relaxed. Parser source and AST indexing limits do not bound PHP parser CPU/memory while building the AST. Browser scans can terminate the Web Worker. The existing GitHub scanner already runs in a disposable Docker container with 256 MiB memory, 0.5 CPU, and a 30-second execution deadline; a new direct server-side PHP parsing path should retain an equivalent process/container boundary. The standalone local CLI has no hard parser-time deadline, so avoid running it on hostile repositories without an external process timeout and memory limit. Table references from SQL literals and recognized model calls are best effort. AngularJS registration ownership is best effort when one file contains several components. Domain labels reflect names only and do not establish reachability. Review source at the cited line before treating any relationship or risk as verified.

## Cross-stack frontend/PHP evidence

The graph correlates statically extracted `fetch`, Axios, AngularJS `$http`, and a narrowly recognized AngularJS `Upload.upload` wrapper with supported CodeIgniter 3/4 and Laravel route declarations. The wrapper is resolved only when one selected service definition directly forwards a call argument to the upload config's `url`; the frontend call and wrapper definition references are both preserved. A wrapper name does not establish an HTTP method, so the method remains unknown unless source explicitly sets one. Correlation removes a leading `index.php/` from frontend paths, strips query/fragment text, trims edge slashes, preserves case, and compares whole path segments. Only documented CodeIgniter placeholders (`(:num)`, `(:alpha)`, `(:alphanum)`, `(:any)`, `(:segment)`, terminal `(:all)`) and Laravel `{name}` / `{name?}` segments are treated as parameters; unsupported pattern syntax is never treated as an exact match. Laravel route parameter constraints are not evaluated, and implicit API prefixes supplied by framework bootstrap are not inferred. Methods are compared when statically known; incompatible methods produce unresolved evidence and no `calls-route` edge. A single exact or parameterized path match creates an inferred `calls-route` edge; without a known frontend method this is not a method-qualified match. Multiple matches, unsupported patterns, dynamic frontend URLs, and no-match cases are retained in optional `crossStack` metadata with source references at both ends; dynamic/unresolved cases do not create route edges.

An inferred frontend-to-route edge does not establish that the frontend and PHP code are deployed together or that a request reaches that server. A route links to a PHP controller method only when the route adapter resolves a unique declared method. For CI3 routes, static `$1` forwarding is recorded only when the route placeholder and controller argument are both explicit; a uniquely matching `switch` parameter, string case, and same-class handler call can then produce observed parameter-binding and dispatch edges. These edges establish static source relationships, not runtime branch execution. The scanner also emits observed `calls-php-method` edges for explicit `$this->typedProperty->method()` calls with a unique declared target and uniquely declared same-class `$this->method()` calls. Constructor-injected parameters, inherited targets, dynamic receivers, service locators, database writes, and business outcomes are not inferred. Legacy model-call heuristics remain inferred. Optional graph metadata reports unresolved call counts, unsupported forms, and correlation outcomes while preserving schema version 1.0.0 and browser/server shared scanning behavior.

Flagship investigation: `Putdatacrtl::putScore` has guards for CA above 40 and exam score above 60, with writes to `result`. `Putdatacrtl::putPromotion` checks an active session, requires destination class and class operation, checks whether the student's session is the current one, compares current session start with prior session end, then updates and inserts `classes` membership. `Getdatactrl::getPromotion` and `getCollatedResultinput` read class and result data. The AngularJS `promotionCtr` posts to `index.php/reg/putpromotion` and fetches `index.php/gett/getpromotiondata`. This establishes the inspected path only; it does not show that promotion is universally independent of academic results. Possible missing negative-score validation or SQL query risks are hypotheses requiring manual review, never verified vulnerabilities.

Next graph step: render the JSON artifact with node and edge filters, certainty styling, and clickable relative source references. Keep the graph behind an operator workflow and avoid transmitting snippets.

## Project module candidates

The Architecture workspace now derives project-wide module candidates from feature-named graph components and directly recorded relationships. Shared infrastructure receives a separate candidate grouping. Members can overlap: a shared service or table may appear in several modules. The explorer shows candidate domains, associated feature investigations, component source references, internal edges, boundary edges, unclassified components, and scanner warnings. Selecting a member opens its source reference in the Evidence Inspector; **View module in graph** focuses up to the existing 36-node viewport limit. The dashboard counts extracted components and relationships from analyzed allowlisted files, not the entire repository. Candidate boundaries and unresolved questions require source and runtime review before treating them as business behavior.

## Scan from the browser

Open `/`, choose **New Investigation**, then **Scan local repository directory**. The browser asks you to select a folder. The page reads supported selected PHP and JavaScript files locally, applies the same source allowlist and byte/file limits as the CLI, generates a validated graph, and opens it automatically. Download `graph.json` and `manifest.json` from the scan summary. **Import existing graph JSON** remains available. No source file or graph is sent to a server by this workflow.

Browser directory picking requires a browser that supports directory selection and a secure context (HTTPS or localhost). It cannot prove that selected files are free of symlinks, detect files the browser omitted, or inspect unselected directories. The generated graph and manifest state these limits. Use the CLI when filesystem-level symlink protection or a durable local artifact is required. A hosted deployment has the same user-granted directory access limits and must not expose a server scan-by-path endpoint.

For large folders, Chrome may spend time enumerating files before it fires the directory input's `change` event. The page cannot measure or cancel progress inside that native picker. Once Chrome returns the list, the page shows the selected repository and received-file count, validates names and size metadata, and sends only eligible files to a Web Worker. The worker reports actual files and bytes read and processed, then extracts and validates the graph. No percentage is shown because picker enumeration and extraction do not provide a measured total duration. **Cancel scan** terminates the worker; the CLI is the reliable fallback when Chrome cannot finish enumerating a WSL-mounted folder.
