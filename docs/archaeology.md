# Repository intelligence engine

Run locally with `npm run archaeology -- --repo /absolute/path/to/repository`. `ARCHAEOLOGY_REPO_ROOT=/absolute/path/to/repository npm run archaeology:scan` remains supported. Use `--out /absolute/local/output-directory` to select an output folder; the default is `.local-archaeology` under the current directory. The command reads only application PHP and JavaScript plus named application scripts in `assets/js`. It writes `graph.json` and `manifest.json` to the output directory. The default directory is gitignored. Do not commit artifacts from private repositories when using a custom output directory. Import `graph.json` directly into `/` with **Import graph JSON**.

The manifest records the graph schema and snapshot ID, UTC scan time, repository display name, source-derived scan and extraction counts, PHP and JavaScript file detections, warnings, coverage limitations, and artifact filenames. Counts describe scanned files and extracted records, not repository-wide coverage estimates. Neither artifact includes absolute repository paths or source snippets. Scanning runs locally, never executes repository code, and does not call the model provider or expose a server route. A future integration should use a separately installed, user-authorized local companion scanner that returns only validated artifacts to the browser; browser directory selection alone cannot provide reliable unrestricted repository scanning or the same filesystem protections.

The version 1.0.0 graph has a content-derived snapshot ID, typed nodes and edges, relative source references, observed or inferred certainty, extraction method, deterministic order, warnings, and limits. Contents and absolute paths are omitted. The scanner uses deterministic patterns, not a PHP or JavaScript parser. It can miss multiline declarations and dynamic calls, and can mistake strings for code. Table references from SQL literals and recognized model calls are best effort. AngularJS registration ownership is best effort when one file contains several components. Domain labels reflect names only and do not establish reachability. Review source at the cited line before treating any relationship or risk as verified.

Flagship investigation: `Putdatacrtl::putScore` has guards for CA above 40 and exam score above 60, with writes to `result`. `Putdatacrtl::putPromotion` checks an active session, requires destination class and class operation, checks whether the student's session is the current one, compares current session start with prior session end, then updates and inserts `classes` membership. `Getdatactrl::getPromotion` and `getCollatedResultinput` read class and result data. The AngularJS `promotionCtr` posts to `index.php/reg/putpromotion` and fetches `index.php/gett/getpromotiondata`. This establishes the inspected path only; it does not show that promotion is universally independent of academic results. Possible missing negative-score validation or SQL query risks are hypotheses requiring manual review, never verified vulnerabilities.

Next graph step: render the JSON artifact with node and edge filters, certainty styling, and clickable relative source references. Keep the graph behind an operator workflow and avoid transmitting snippets.

## Project module candidates

The Architecture workspace now derives project-wide module candidates from feature-named graph components and directly recorded relationships. Shared infrastructure receives a separate candidate grouping. Members can overlap: a shared service or table may appear in several modules. The explorer shows candidate domains, associated feature investigations, component source references, internal edges, boundary edges, unclassified components, and scanner warnings. Selecting a member opens its source reference in the Evidence Inspector; **View module in graph** focuses up to the existing 36-node viewport limit. The dashboard counts extracted components and relationships from analyzed allowlisted files, not the entire repository. Candidate boundaries and unresolved questions require source and runtime review before treating them as business behavior.

## Scan from the browser

Open `/`, choose **New Investigation**, then **Scan local repository directory**. The browser asks you to select a folder. The page reads supported selected PHP and JavaScript files locally, applies the same source allowlist and byte/file limits as the CLI, generates a validated graph, and opens it automatically. Download `graph.json` and `manifest.json` from the scan summary. **Import existing graph JSON** remains available. No source file or graph is sent to a server by this workflow.

Browser directory picking requires a browser that supports directory selection and a secure context (HTTPS or localhost). It cannot prove that selected files are free of symlinks, detect files the browser omitted, or inspect unselected directories. The generated graph and manifest state these limits. Use the CLI when filesystem-level symlink protection or a durable local artifact is required. A hosted deployment has the same user-granted directory access limits and must not expose a server scan-by-path endpoint.

For large folders, Chrome may spend time enumerating files before it fires the directory input's `change` event. The page cannot measure or cancel progress inside that native picker. Once Chrome returns the list, the page shows the selected repository and received-file count, validates names and size metadata, and sends only eligible files to a Web Worker. The worker reports actual files and bytes read and processed, then extracts and validates the graph. No percentage is shown because picker enumeration and extraction do not provide a measured total duration. **Cancel scan** terminates the worker; the CLI is the reliable fallback when Chrome cannot finish enumerating a WSL-mounted folder.
