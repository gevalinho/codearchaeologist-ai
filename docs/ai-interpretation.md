# Phase 6.2 AI interpretation

The Workflows feature view offers an explicit **AI · interpretation** tab. Selecting a feature never calls a model. A user must review the bounded packet and check the consent box before a request is sent. Overview offers a separate **Repository overview** AI scope with its own review and consent control. Switching from Overview to Selected feature opens the feature AI tab; no conversation is carried between scopes.

The versioned packet is built from the selected graph and deterministic feature investigation. It contains at most 12 components, 16 relationships, and 12 observed rule patterns, plus classification and a brief deterministic proposal summary. The graph artifact stores source paths and line ranges but no source bodies. Accordingly, packets contain **no source excerpts**; browser-local source is not read by the server. Missing method bodies and runtime verification remain explicit limitations. Paths matching common credential or secret names are excluded. The server accepts only this references-only packet shape and a 20 KB request.

The repository packet uses a separate versioned shape and a maximum of 40 unique source-line references within 16 KB. It samples candidate anchors first, preferring specific candidates over generic Core names, then adds representative components, relationships, and rule-pattern labels across candidates. It includes candidate classifications, evidenced language indicators, analyzed-file count, represented and omitted candidate-group counts, and truncation status. Candidate names and classifications remain static findings, not proof of working features. The repository answer schema marks observed structure, inference, suggestion, or insufficient evidence. Purpose inferences require two distinct candidate-anchor citations; named candidates require their own anchor citation. These checks prove packet membership and basic provenance, not semantic truth.

GitHub graph artifacts may carry validated source coverage counts. Both AI packet types include those counts when present. The UI labels partial analyses beside AI answers, and model instructions require stating that omitted source may contain additional components or relationships. No omitted file names or contents are sent to the provider.

The workspace activity bar also opens a right-side AI assistant from any section. Repository overview is the default scope; Selected feature is available after a feature is explicitly selected. The drawer sends a question directly through the same chat route without running a separate interpretation request. Its first Send opens an inline review and consent step. Consent is held in memory for the exact serialized packet and scope, and a new artifact resets the drawer context. Each scope and feature has an isolated in-memory conversation; only the last three question/answer pairs are sent with a follow-up. Neither conversations nor evidence are stored in browser persistence. The older Overview and Workflows AI panels remain available for their existing interpretation flows.

The server route is available only in development with `ENABLE_FEATURE_AI=1`, `ENABLE_DEV_FEATURE_AI=1`, and a localhost `FEATURE_AI_ORIGIN`. It reuses `INVESTIGATION_PROVIDER` and its server-only provider API key. Requests require same-origin headers and explicit consent. Private-origin packets additionally require an active GitHub App session. No AI access key is sent from the browser. Production AI is disabled until authenticated application sessions and a shared rate limiter are implemented. The service limits concurrency, cooldown, model duration, output tokens, and validates every response claim or chat answer against evidence IDs. Provider failures and malformed responses return a recoverable error without model text or credentials. Chat sends at most three recent question/answer pairs and the same bounded references-only packet; switching features resets the conversation.

The interpretation output budget defaults to 3,000 tokens. `FEATURE_AI_MAX_OUTPUT_TOKENS` can set an integer from 512 through 4,000; invalid values fail closed. The 30-second overall deadline, provider timeouts, evidence limits, and output validator are unchanged. The prompt requests only a few short claims and one or two evidence IDs per claim, rather than repeating the full packet. A provider `finish_reason: length` remains an error even if the returned text parses as JSON.

Evidence IDs prove only that a cited record is in the packet. They do not prove the model's interpretation is semantically correct. The UI labels purpose and workflow claims as interpretations, modernization as suggestions, and retains uncertainty. AI output never edits the graph or deterministic reconstruction specification. The optional preview handoff opens the existing synthetic preview. `Password.php` is allowed only in recognized PHP controller directories; credential and secret filenames remain filtered.

Limitations: the client-provided packet is not a server-authenticated reconstruction of the graph. Its origin and contents must be treated as user-supplied data; the access key gates the endpoint and the provider receives only the packet the user reviewed. Browser-local and imported artifacts cannot be independently verified server-side. An in-memory cooldown applies per server process, so multi-instance deployments need a shared rate limiter before public exposure. Do not enable this feature for untrusted users without stronger server-side authentication and quota controls.

## Autonomous investigation MVP

The workspace assistant offers a separate **Investigate** mode. Before the first investigation on an artifact, the user reviews a broader consent scope: the app server receives the validated graph artifact (maximum 5 MB) and may send up to 40 sanitized source references in a maximum 16 KB packet to the configured external model. The graph artifact has no source bodies. Consent is kept only in the current browser session and resets when a new artifact replaces the graph. Normal chat remains separate.

The development-only `/api/autonomous-investigation` route validates the graph again, enforces same-origin and consent checks, and requires an active GitHub App session for private-origin requests. Production remains disabled. A per-process active-request gate and ten-second cooldown limit repeat calls; multi-instance production needs authenticated sessions and a distributed rate limiter. The route streams completed read-only tool actions and the validated report as bounded JSON lines. The browser can abort the request. The server enforces a 45-second investigation deadline, three tool calls maximum, two graph hops maximum, and bounded provider outputs (400 tokens per action, 900 for the report).

Tools search components, trace relationships, inspect static rule patterns, find name-based feature hypotheses, and check coverage. Tool names and arguments are validated before execution. Results come only from the validated graph and are filtered for safe labels and source references. The final answer is checked with repository citation validation, including independent candidate anchors for inference. Tool citations establish packet membership, not semantic truth. No repository code, shell command, dependency, or URL is executed or fetched. Failed tool calls or provider output stop the investigation without a fabricated report. Live Muse Spark investigation remains unverified until a user runs a consented local test.

Component search indexes validated node IDs, names, kinds, and source paths with case-insensitive token matching; the exact term `authentication` is normalized to `auth` for common abbreviated component names. Search feedback records the normalized term and match count without logging paths. An identical empty search is rejected before execution and the model gets one bounded chance to pick a different query or tool. Three distinct empty searches produce a deterministic insufficient-evidence report with the real terms searched and partial-coverage disclosure. This only establishes that those terms had no matches in the analyzed subset. Final validation failures stream stable safe categories and rule identifiers; raw model output is not returned.

The action and final-report requests are separate structured provider calls. An action uses `tool`, `query`, `componentId`, and `depth`; a final report uses `schemaVersion`, `status`, `answer`, `evidenceIds`, and `uncertainty`. A short `{ "tool": "finish" }` is accepted only as a termination action; arbitrary extra fields and report content in the action response are rejected. The server allows one corrective action proposal for a malformed action or duplicate search. Identical successful searches are also skipped because they cannot add new graph results. If the model repeats a completed search again, the loop proceeds to the final-report request without executing the duplicate. The three-tool cap remains unchanged. Action validation and final-report validation have distinct safe error categories; malformed provider JSON remains a provider error, and invalid citations or unsafe report text remain hard failures.
