# GitHub App connection and private repository scans

Create a **dedicated CodeArchaeologist GitHub App**. Set repository permissions to **Contents: Read-only** and **Metadata: Read-only**. Request no write permissions. Enable user authorization. Configure the user authorization callback URL as `https://YOUR-ORIGIN/api/github-app/callback` and the installation setup URL as `https://YOUR-ORIGIN/api/github-app/install/callback`. For local development, use `http://localhost:3000` consistently in both URLs and `GITHUB_APP_ORIGIN`. Install the app for **selected repositories** when possible.

The browser user sign-in proves the GitHub account identity. Installation selection grants the app access to repositories. The server lists installations and repositories using the user's short-lived GitHub App user token, then creates a repository-scoped installation token for acquisition. A browser-supplied installation or repository ID is never trusted by itself. The installation callback does not grant access; the server checks GitHub's current repository list at job creation, before acquisition, after scanning, and before private artifact retrieval.

## Configuration

Set the server-only variables listed in `.env.example`: `GITHUB_APP_ID`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_SESSION_SECRET`, `GITHUB_APP_ORIGIN`, `CODEARCH_DB_PATH`, `CODEARCH_TOKEN_ENCRYPTION_KEY`, and `CODEARCH_TOKEN_KEY_VERSION`. Keep the private key, client secret, session secret, and encryption key in ignored local secrets or a production secret store. Do not put them in browser variables. The app private key can be supplied as a PEM string with literal `\n` separators. Use a distinct 32-byte-or-longer random session secret. Serve production over HTTPS.

`CODEARCH_DB_PATH` must be an absolute path in an existing directory owned by the application user with mode 0700. The database file is created with mode 0600; an existing file must also be private and regular. Generate the encryption key with `openssl rand -base64 32` and store the output privately as `CODEARCH_TOKEN_ENCRYPTION_KEY`. Set `CODEARCH_TOKEN_KEY_VERSION=1` for the first key. The key must be exactly 32 decoded bytes and is distinct from `GITHUB_APP_SESSION_SECRET`. Keep the database on local, encrypted storage. Do not commit the key or database. Back up the database and key separately with restricted access. Rotating to a new version invalidates existing sessions and requires users to reconnect; it does not migrate existing ciphertext.

The server runs an additive `github_sessions` schema migration when it first opens the database. It refuses a database with a newer schema version. Session handles are stored only as SHA-256 hashes; GitHub user tokens are encrypted with AES-256-GCM and bound to the handle hash and user ID. The database contains no plaintext GitHub access token. Node.js 24.15 or newer in the 24.x line is required for the built-in `node:sqlite` driver; no native SQLite package is required. The pinned Node 24 runtime must be tested on each deployment.

Docker remains required, as described in [GitHub ingestion](github-ingestion.md). The installation token is used only by the acquisition process and never passed to the Docker scanner. No repository code runs, and no source is sent to a model. The existing public URL flow and deployment access key remain separate.

For Phase B2, set `CODEARCH_ARTIFACT_DIR` and `CODEARCH_STAGING_DIR` to separate absolute directories outside the checkout, build output, or release directories. Create each directory before starting the app, owned by the app user with mode 0700. The job migration adds `github_jobs` and `github_artifacts` tables to the B1 SQLite database and advances the schema from version 1 to version 2. It does not alter existing sessions. Graph and manifest files are generated with private 0600 permissions, SHA-256 checksums, and a five-minute expiry. Startup marks interrupted scans failed; it does not rerun them. Expiry sweeps remove database records and orphan artifact files. On startup, only staging directories with the scanner's generated name pattern are removed; unrelated paths and symlinks are left untouched. Keep the database and artifact directory on persistent local storage and back them up consistently if scan results must survive host loss. Staged source remains temporary and is deleted after each scan.

The session cookie contains an opaque handle only; the GitHub user token is encrypted in the durable session database. Sessions last no longer than eight hours and are revoked on logout. Sessions, job status, and completed artifacts now survive process restarts; interrupted scans become failed and require a new scan. A GitHub 401 while refreshing repositories revokes the session and asks the user to reconnect; other GitHub authorization failures do not grant repository access. There is no token refresh or webhook-driven immediate revocation in this phase; authorization is checked when each private job or artifact is accessed. Already downloaded graph data in a user's browser cannot be remotely erased after a GitHub permission change; users should close shared browser sessions and disconnect. A single-process deployment is still required because rate limits and active job controllers are process-local until B3. Browser downloads are controlled by the authorized user and cannot be revoked once saved. Production AI remains disabled, and public scanning still uses its existing controlled access key until later phases.

## Manual acceptance

1. Configure the App and Docker on the server; restart it. Open `/` in a fresh browser and choose **Connect GitHub**. Verify GitHub redirects to `/api/github-app/callback`, then back to `/` without a token in the URL or browser storage.
2. Choose **Authorize repositories**, install for one private repository, return to `/`, and refresh repositories. Verify its owner, name, private status, and installation ID are shown. With multiple installations, verify each authorized repository appears under the correct installation.
3. Select the private repository and start analysis. Observe the real job stages. When ready, verify the graph loads, modules and evidence are usable, and both artifacts download. Confirm source references remain relative paths.
4. Sign in as a second GitHub user without repository access. Verify the private repository is absent, its numeric IDs cannot create a scan, and its job status and artifacts return 404 even if the job ID is known.
5. Remove repository access or uninstall the App. Refresh the connection and try a new scan; it must fail. Try downloading an existing private artifact; it must be unavailable. Reinstall and reconnect, then retry.
6. Cancel a running job. Verify it stops, artifacts are unavailable, and temporary source directories are removed. Check Docker has no residual scanner container and no Docker socket was mounted into the scanner.
7. Disconnect. Verify the session is gone and the in-browser graph is cleared. Reopen a fresh browser and confirm no private graph or artifacts appear without authorization.
8. Exercise the existing public URL, browser directory, and JSON import paths. They must still work independently.
