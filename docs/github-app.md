# GitHub App connection and private repository scans

Create a **dedicated CodeArchaeologist GitHub App**. Set repository permissions to **Contents: Read-only** and **Metadata: Read-only**. Request no write permissions. Enable user authorization. Configure the user authorization callback URL as `https://YOUR-ORIGIN/api/github-app/callback` and the installation setup URL as `https://YOUR-ORIGIN/api/github-app/install/callback`. For local development, use `http://localhost:3000` consistently in both URLs and `GITHUB_APP_ORIGIN`. Install the app for **selected repositories** when possible.

The browser user sign-in proves the GitHub account identity. Installation selection grants the app access to repositories. The server lists installations and repositories using the user's short-lived GitHub App user token, then creates a repository-scoped installation token for acquisition. A browser-supplied installation or repository ID is never trusted by itself. The installation callback does not grant access; the server checks GitHub's current repository list at job creation, before acquisition, after scanning, and before artifact retrieval for App-selected repositories, whether public or private.

## Configuration

Set the server-only variables listed in `.env.example`: `GITHUB_APP_ID`, `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET`, `GITHUB_APP_SLUG`, `GITHUB_APP_PRIVATE_KEY`, `GITHUB_APP_SESSION_SECRET`, `GITHUB_APP_ORIGIN`, `CODEARCH_DB_PATH`, `CODEARCH_TOKEN_ENCRYPTION_KEY`, and `CODEARCH_TOKEN_KEY_VERSION`. Keep the private key, client secret, session secret, and encryption key in ignored local secrets or a production secret store. Do not put them in browser variables. The app private key can be supplied as a PEM string with literal `\n` separators. Use a distinct 32-byte-or-longer random session secret. Serve production over HTTPS.

`CODEARCH_DB_PATH` must be an absolute path in an existing directory owned by the application user with mode 0700. The database file is created with mode 0600; an existing file must also be private and regular. Generate the encryption key with `openssl rand -base64 32` and store the output privately as `CODEARCH_TOKEN_ENCRYPTION_KEY`. Set `CODEARCH_TOKEN_KEY_VERSION=1` for the first key. The key must be exactly 32 decoded bytes and is distinct from `GITHUB_APP_SESSION_SECRET`. Keep the database on local, encrypted storage. Do not commit the key or database. Back up the database and key separately with restricted access. Rotating to a new version invalidates existing sessions and requires users to reconnect; it does not migrate existing ciphertext.

The server runs an additive `github_sessions` schema migration when it first opens the database. It refuses a database with a newer schema version. Session handles are stored only as SHA-256 hashes; GitHub user tokens are encrypted with AES-256-GCM and bound to the handle hash and user ID. The database contains no plaintext GitHub access token. Node.js 24.15 or newer in the 24.x line is required for the built-in `node:sqlite` driver; no native SQLite package is required. The pinned Node 24 runtime must be tested on each deployment.

Docker remains required, as described in [GitHub ingestion](github-ingestion.md). The installation token is used only by the acquisition process and never passed to the Docker scanner. No repository code runs, and no source body is sent to a model. Phase B4 requires a valid GitHub App session for public and private scans; the browser deployment access key has been removed.

For Phase B2, set `CODEARCH_ARTIFACT_DIR` and `CODEARCH_STAGING_DIR` to separate absolute directories outside the checkout, build output, or release directories. Create each directory before starting the app, owned by the app user with mode 0700. The job migration adds `github_jobs` and `github_artifacts` tables to the B1 SQLite database and advances the schema from version 1 to version 2. It does not alter existing sessions. Graph and manifest files are generated with private 0600 permissions, SHA-256 checksums, and a five-minute expiry. A scan with an expired or absent B3 lease is marked interrupted and never rerun; an unexpired lease may belong to another live process. Expiry sweeps remove database records and orphan artifact files. On startup, only staging directories with the scanner's generated name pattern and at least two minutes of age are removed when no scan lease is active; unrelated paths and symlinks are left untouched. Keep the database and artifact directory on persistent local storage and back them up consistently if scan results must survive host loss. Staged source remains temporary and is deleted after each scan.

Phase B3 advances the same SQLite database to schema version 3 with `quota_events`, `quota_leases`, and `provider_usage`. SQLite write transactions reserve quotas and global scan/AI slots across connections. Demo defaults are 10 OAuth starts per 15 minutes globally, 5 installation starts per authenticated user per 15 minutes, 2 scan starts per authenticated user per hour, 6 AI starts per user per hour, and 2 autonomous starts per hour plus 6 per day. One scan and one paid AI workflow may run globally. OAuth login uses one global bucket because the application does not have a trusted client IP from the reverse proxy; it deliberately ignores arbitrary forwarded IP headers. `CODEARCH_AI_DAILY_ATTEMPTS` (default 40) and `CODEARCH_AI_DAILY_TOKENS` (default 250000) are configurable positive integers. Every Baseten or Meta HTTP attempt, including retries and each autonomous step, consumes one attempt and a conservative token reservation based on the bounded request bytes plus maximum output tokens. The token reservation is not refunded after failed attempts. Provider-reported actual token use is recorded separately. Quota records older than one day, expired leases, and old daily usage rows are swept on reservations. A live scanner renews its lease during work and cleanup; a terminated process cannot renew, so the lease expires. Configure these ceilings for provider pricing before enabling any future production AI access.

The session cookie contains an opaque handle only; the GitHub user token is encrypted in the durable session database. Sessions last no longer than eight hours and are revoked on logout. Protected scan and production AI requests verify the OAuth token against GitHub before admitting work; a GitHub 401 revokes the durable session. Private artifact access also rechecks installation and repository permission. Job status and completed artifacts survive process restarts; interrupted scans require a new scan. Already downloaded graph data in a user's browser cannot be remotely erased after a GitHub permission change. Public jobs created before B4 have no owner and are inaccessible through the B4 routes until they expire. Browser downloads are controlled by the authorized user and cannot be revoked once saved. Production AI requires both `ENABLE_FEATURE_AI=1` and `ENABLE_PRODUCTION_AI=1`; the latter is unset by default. GitHub-origin AI requests require a user-owned job ID and an exact match to the server-generated evidence packet or graph. Browser-local and imported graphs remain user-supplied metadata and cannot be independently authenticated against GitHub.

## Manual acceptance

1. Configure the App and Docker on the server; restart it. Open `/` in a fresh browser and choose **Connect GitHub**. Verify GitHub redirects to `/api/github-app/callback`, then back to `/` without a token in the URL or browser storage.
2. Choose **Authorize repositories**, install for one private repository, return to `/`, and refresh repositories. Verify its owner, name, private status, and installation ID are shown. With multiple installations, verify each authorized repository appears under the correct installation.
3. Select the private repository and start analysis. Observe the real job stages. When ready, verify the graph loads, modules and evidence are usable, and both artifacts download. Confirm source references remain relative paths.
4. Sign in as a second GitHub user without repository access. Verify the private repository is absent, its numeric IDs cannot create a scan, and its job status and artifacts return 404 even if the job ID is known.
5. Remove repository access or uninstall the App. Refresh the connection and try a new scan; it must fail. Try downloading an existing private artifact; it must be unavailable. Reinstall and reconnect, then retry.
6. Cancel a running job. Verify it stops, artifacts are unavailable, and temporary source directories are removed. Check Docker has no residual scanner container and no Docker socket was mounted into the scanner.
7. Disconnect. Verify the session is gone and the in-browser graph is cleared. Reopen a fresh browser and confirm no private graph or artifacts appear without authorization.
8. Exercise the existing public URL, browser directory, and JSON import paths. They must still work independently.
